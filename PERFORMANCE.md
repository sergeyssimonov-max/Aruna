# Стратегия производительности

## Принципы (в порядке приоритета)

1. **Корректность и читаемость важнее скорости.**  
   Любая оптимизация, которую нельзя легко объяснить и измерить, подлежит удалению.

2. **Сначала измеряй, потом оптимизируй.**  
   Никаких изменений «потому что так быстрее» без цифр до/после.

3. **Минимальный стек.**  
   Стандартная библиотека + `memchr` там, где это реально помогает.  
   Новые зависимости ради микрооптимизаций запрещены.

4. **Параллелизм — только по делу.**  
   Rayon и подобное разрешены только при доказанном ускорении ≥ 1.5–2× на реальной нагрузке.  
   (ZIP-распаковка занимает ~72 % прогона и не параллелится через один `ZipArchive`.
   Разбор — остальные ~28 %, так что даже мгновенный разбор дал бы 1.4×. Rayon убран.)

5. **`unsafe` — только на границе.**  
   Допустим исключительно на FFI / WASM ABI и только с полными `// SAFETY:` комментариями.  
   `unsafe` «на всякий случай» или ради микрооптимизаций запрещён.

6. **Публичный API не ломаем** без явного согласования.

## Как измерять

- Wall-clock полного прогона (`time ./target/release/aruna` или fixture ZIP).
- По стадиям (`read` / `parse` / `sort` / `render`) — `cli/examples/bench_parse.rs`,
  min-median-max по `ARUNA_BENCH_RUNS` прогонам, без сторонних зависимостей:
  `cargo run --release --example bench_parse -- fixtures/…zip`.
- Разбор отдельно — `cli/examples/bench_fields.rs`: архив читается один раз,
  дальше измеряются только нарезка окон (`Windows::of`) и чтение полей
  (`parse_windows`) на уже подготовленных окнах. `ARUNA_BENCH_WINDOW` обрезает
  окна — это и отвечает на вопрос, за чем следует цена: за байтами или за
  документами.
- Сортировка отдельно — `cli/examples/bench_order.rs`: архив читается один раз,
  дальше измеряется только `order::sort_records`, на свежей копии каждый прогон.
  Стоимость копии печатается отдельной строкой и в результат не входит;
  `ARUNA_BENCH_WARMUP` прогонов не записываются.
- Пиковая память — `/usr/bin/time -l` (macOS) или `-v` (Linux) вокруг команды.
- Для WASM — latency поиска в браузере (Performance-профиль вкладки).

Измерительный код в программе не исполняется: конвейер обобщён по `Probe`, и
`parse_zip` монодоморфизируется с реализацией без часов, тогда как
`parse_zip_timed` — с той, что считает. Стадия закрывается там, где работа
действительно заканчивается: если сдвинуть отметку, стадия «подешевеет», не
изменив программу. Это ровно та ошибка, на которой уже один раз получили
мнимые −110 мс.

## Текущий профиль

Замеры на `cli/fixtures/TLHbasisONLINE25_1_ZENODO_Beta_03.zip` (23 936 манускриптов),
release, 9 прогонов, медиана, Apple Silicon. Сеть и запись файла сюда не входят.

| Стадия          | Медиана   | Доля  |
|-----------------|-----------|-------|
| read (zip)      | 870 мс    | 79 %  |
| parse           | 219 мс    | 20 %  |
| sort            | 5 мс      | 0.5 % |
| render html     | 6 мс      | 0.6 % |
| **итого**       | 1097 мс   |       |

Разбор идёт потоком: запись разбирается и окно освобождается до чтения
следующей, поэтому «read» и «parse» замеряются внутри одного прохода, а не
вокруг двух. Пиковый RSS — 36–38 МБ.

### Из чего состоит `parse`

Замерено `bench_fields` на трёх размерах окна (16 / 4 / 1 КиБ):

| Окно | Байт окон | Чтение полей | Пропускная |
|------|----------:|-------------:|-----------:|
| 16 КиБ | 173,8 МиБ | 325,9 мс | 533 МиБ/с |
| 4 КиБ  |  80,9 МиБ | 198,8 мс | 407 МиБ/с |
| 1 КиБ  |  23,4 МиБ |  91,2 мс | 256 МиБ/с |

Линейная подгонка по крайним точкам: **1,56 мс на МиБ окон** плюс **54,7 мс**
постоянных на 23 936 документов. То есть примерно **83 % цены разбора следует за
байтами окна** и **17 % — за числом документов** (2,3 мкс на запись:
аллокации полей и сборка записи).

Предельная скорость сканирования выходит 641 МиБ/с при том, что нарезка окон —
один проход — идёт на 16 207 МиБ/с. Разрыв в 25 раз означал, что окно обходится
многократно.

### Кто именно обходил

`bench_fields --features bench` меряет каждый извлекатель по отдельности, в том
порядке и с теми же условиями, в каких их вызывает `parse_windows`. Оказалось,
что дело не во всех семи, а в одном:

| Извлекатель   | Было     | Стало   |
|---------------|---------:|--------:|
| `inv`         | 212,5 мс | 93,3 мс |
| `lang`        |  64,4 мс | 63,1 мс |
| `editor+year` |  35,2 мс | 34,5 мс |
| `sigla`       |   3,9 мс |  3,8 мс |
| year fallback |   2,2 мс |  2,2 мс |
| `corpus`      |   1,1 мс |  1,1 мс |
| `cth`         |   0,8 мс |  0,8 мс |
| **разбор**    | **325 мс** | **204 мс** |

`extract_inv` искал элемент шестью вызовами `find_open_tag` — два окна на три
написания, — а каждый такой вызов обходит *все* теги стога. Два из шести были
заведомо лишними: сравнение имён регистронезависимое, поэтому `InvNr` и `invNr`
— один и тот же вопрос. И поле есть лишь у 11,6 % записей, так что 88 %
документов прогоняли все шесть проходов до конца.

Заменено на `xml_scan::find_open_tags` — один обход стога, первое вхождение для
каждого имени сразу. Порядок предпочтений сохранён: выигрывает первый элемент
предпочтительного написания, и только если он пуст, очередь переходит
следующему. Каталог из 23 936 записей после замены байт в байт прежний.

`sort` вынесен из `parse` отдельной стадией: это разные затраты с разными
причинами — одна растёт с архивом, другая с описью, — и в сумме ни одну из них
не было видно.

Воспроизводится тремя командами:

```
cargo run --release --example bench_parse -- cli/fixtures/…zip
cargo run --release --example bench_order -- cli/fixtures/…zip
cargo run --release --features bench --example bench_fields -- cli/fixtures/…zip
```

## Поиск в браузере

Chrome на macOS, dev-сервер, настоящая опись (23 936 манускриптов), wasm-движок.
Задержка ответа воркера: `postMessage` → `result`, медиана из 25 повторов.

| Запрос     | Совпадений | Медиана |
|------------|-----------:|--------:|
| `k`        | 650 групп  | 0.7 мс  |
| `kbo`      | 555 групп  | 0.7 мс  |
| `hit`      | 591 группа | 0.9 мс  |
| `schwemer` | 50 групп   | 0.4 мс  |
| `zzzznope` | 0          | 0.4 мс  |

Сквозная задержка от нажатия до обновлённого счётчика в шапке — 18–27 мс
медианы: это отрисовка списка, а не поиск. Замеры сделаны на снятом
веб-приложении (React, виртуальный список) и сохранены как исторические: они
описывают поиск, а не тот интерфейс, и настольное приложение их ещё не
повторяло.

Скрипты замеров лежат вне репозитория и обращались к `/src/lib/search.worker.ts`
и `/src/data/inventory.bin.gz` — обоих файлов больше нет, они удалены вместе с
сайтом 2026-08-23. Воспроизвести эти числа в нынешнем дереве нельзя; чтобы
сравнивать с ними дальше, замеры нужно поставить заново на настольном
приложении.

## Что уже решено замерами

| Место              | Результат                          | Решение          |
|--------------------|------------------------------------|------------------|
| Rayon в archive.rs | parse 115 мс без него против 18 мс с ним; на полном прогоне 1495 мс против 1389 мс — 1.07×. На нынешнем профиле разбор дороже, но потолок всё равно 1.21×: столько дал бы разбор ценой в ноль | Удалён: ниже порога 1.5–2× из принципа 4 |
| ZIP-распаковка     | 887 мс из 1229 мс (72 %), один `ZipArchive` не читается параллельно | Оставляем как есть |
| Поиск `AO:InvNr` вне заголовка | parse 120 мс → 294 мс: номер лежит в теле документа, и без просмотра широкого окна колонка была пуста у всех 24 000 записей | Оставлено: пустая колонка хуже 10 % прогона |
| `PoolHits`: маска по размеру пула вместо одного `u64` | Задержка ответа не изменилась: медианы совпали до 0.1 мс на восьми запросах (`k` 0.7, `kbo` 0.7, `hit` 0.9, `schwemer` 0.4, `zzzznope` 0.4 — одинаково до и после). Замерено переключением модуля на прежнюю версию и обратно | Оставлено: потолок пула стал 255 бесплатно |
| Один обход разметки вместо трёх (`xml_scan::Tags`) | parse 291 → 328 мс, полный прогон 1668 → 1698 мс (+1.8 %). Каталог из 23 936 записей — байт в байт прежний | Оставлено: три копии цикла успели разойтись между собой, принцип 1 ставит читаемость выше 2 % |
| Потоковый разбор вместо сбора корпуса в память | Пик памяти 231 → 48 МБ, полный прогон 1.78 → 1.71 с (три прогона подряд каждой версии). Каталог байт в байт прежний | Сделано ради надёжности: память больше не растёт вместе с архивом |
| simd_scan → xml_scan | Читаемость + честное имя         | Выполнено        |

Числа в этом файле относятся к сборке, на которой сняты, и устаревают вместе с
парсером — доля ZIP была 91 %, пока разбор не начал искать инвентарный номер в
теле документа. Правя профиль, перезамеряйте, а не пересчитывайте.

## Правило для будущих изменений

Любая новая «оптимизация» обязана иметь:
- цифры до/после,
- краткое обоснование,
- отсутствие заметного ухудшения читаемости.

Иначе — откат.

Это отправная точка для будущих бюджетов, а не сами бюджеты: назначать порог
раньше, чем есть baseline, значит закреплять случайное число.

### Ограничения этих измерений

- `bench_export` для стадии «normalise» держит 30.1 МиБ документов в памяти и
  повторяет проход по ним: данные полностью помещаются в кэш, поэтому названная
  пропускная способность (~34 ГиБ/с) относится к прогретому кэшу, а не к рабочей
  нагрузке, где каждый документ читается из архива один раз.
- Одна машина, один запуск подряд. Ни p99, ни распределение по холодному старту
  не снимались.
- Число аллокаций, дескрипторов и объём ввода-вывода не измерялись: в проекте нет
  для этого инструментов, а добавлять их без задачи преждевременно.
