# Стратегия производительности

## Принципы (в порядке приоритета)

1. **Корректность и читаемость важнее скорости.**  
   Любая оптимизация, которую нельзя легко объяснить и измерить, подлежит удалению.

2. **Сначала измеряй, потом оптимизируй.**  
   Никаких изменений «потому что так быстрее» без цифр до/после.

3. **Минимальный стек.**  
   Стандартная библиотека + `memchr` там, где это реально помогает.  
   Новые зависимости ради микрооптимизаций запрещены.

4. **Параллелизм — только по делу.**  
   Rayon и подобное разрешены только при доказанном ускорении ≥ 1.5–2× на реальной нагрузке.  
   (ZIP-распаковка занимает ~72 % прогона и не параллелится через один `ZipArchive`.
   Разбор — остальные ~28 %, так что даже мгновенный разбор дал бы 1.4×. Rayon убран.)

5. **`unsafe` — только на границе.**  
   Допустим исключительно на FFI / WASM ABI и только с полными `// SAFETY:` комментариями.  
   `unsafe` «на всякий случай» или ради микрооптимизаций запрещён.

6. **Публичный API не ломаем** без явного согласования.

## Как измерять

- Wall-clock полного прогона (`time ./target/release/aruna` или fixture ZIP).
- По стадиям (`read` / `parse` / `sort` / `render`) — `cli/examples/bench_parse.rs`,
  min-median-max по `ARUNA_BENCH_RUNS` прогонам, без сторонних зависимостей:
  `cargo run --release --example bench_parse -- fixtures/…zip`.
- Сортировка отдельно — `cli/examples/bench_order.rs`: архив читается один раз,
  дальше измеряется только `order::sort_records`, на свежей копии каждый прогон.
  Стоимость копии печатается отдельной строкой и в результат не входит;
  `ARUNA_BENCH_WARMUP` прогонов не записываются.
- Пиковая память — `/usr/bin/time -l` (macOS) или `-v` (Linux) вокруг команды.
- Для WASM — latency поиска в браузере (Performance-профиль вкладки).

Измерительный код в программе не исполняется: конвейер обобщён по `Probe`, и
`parse_zip` монодоморфизируется с реализацией без часов, тогда как
`parse_zip_timed` — с той, что считает. Стадия закрывается там, где работа
действительно заканчивается: если сдвинуть отметку, стадия «подешевеет», не
изменив программу. Это ровно та ошибка, на которой уже один раз получили
мнимые −110 мс.

## Текущий профиль

Замеры на `cli/fixtures/TLHbasisONLINE25_1_ZENODO_Beta_03.zip` (23 936 манускриптов),
release, 9 прогонов, медиана, Apple Silicon. Сеть и запись файла сюда не входят.

| Стадия          | Медиана   | Доля  |
|-----------------|-----------|-------|
| read (zip)      | 876 мс    | 71 %  |
| parse           | 342 мс    | 28 %  |
| sort            | 4 мс      | 0.3 % |
| render html     | 6 мс      | 0.5 % |
| **итого**       | 1228 мс   |       |

Разбор идёт потоком: запись разбирается и окно освобождается до чтения
следующей, поэтому «read» и «parse» замеряются внутри одного прохода, а не
вокруг двух. Пиковый RSS — 36–38 МБ.

`sort` вынесен из `parse` отдельной стадией: это разные затраты с разными
причинами — одна растёт с архивом, другая с описью, — и в сумме ни одну из них
не было видно.

Воспроизводится двумя командами:

```
cargo run --release --example bench_parse -- cli/fixtures/…zip
cargo run --release --example bench_order -- cli/fixtures/…zip
```

## Поиск в браузере

Chrome на macOS, dev-сервер, настоящая опись (23 936 манускриптов), wasm-движок.
Задержка ответа воркера: `postMessage` → `result`, медиана из 25 повторов.

| Запрос     | Совпадений | Медиана |
|------------|-----------:|--------:|
| `k`        | 650 групп  | 0.7 мс  |
| `kbo`      | 555 групп  | 0.7 мс  |
| `hit`      | 591 группа | 0.9 мс  |
| `schwemer` | 50 групп   | 0.4 мс  |
| `zzzznope` | 0          | 0.4 мс  |

Сквозная задержка от нажатия до обновлённого счётчика в шапке — 18–27 мс
медианы: это React и виртуальный список, а не поиск.

Скрипты замеров лежат вне репозитория; воспроизводятся своим воркером к
`/src/lib/search.worker.ts` и файлом `/src/data/inventory.bin.gz`, как их берёт
приложение.

## Правило для будущих изменений

Любая новая «оптимизация» обязана иметь:
- цифры до/после,
- краткое обоснование,
- отсутствие заметного ухудшения читаемости.

Иначе — откат.
