# Стратегия производительности

## Принципы (в порядке приоритета)

1. **Корректность и читаемость важнее скорости.**  
   Любая оптимизация, которую нельзя легко объяснить и измерить, подлежит удалению.

2. **Сначала измеряй, потом оптимизируй.**  
   Никаких изменений «потому что так быстрее» без цифр до/после.

3. **Минимальный стек.**  
   Стандартная библиотека + `memchr` там, где это реально помогает.  
   Новые зависимости ради микрооптимизаций запрещены.

4. **Параллелизм — только по делу.**  
   Rayon и подобное разрешены только при доказанном ускорении ≥ 1.5–2× на реальной нагрузке.  
   (ZIP-распаковка занимает ~82 % прогона и не параллелится через один `ZipArchive`.
   Разбор заголовков — ~18 %, так что даже мгновенный разбор дал бы 1.21×. Rayon убран.)

5. **`unsafe` — только на границе.**  
   Допустим исключительно на FFI / WASM ABI и только с полными `// SAFETY:` комментариями.  
   `unsafe` «на всякий случай» или ради микрооптимизаций запрещён.

6. **Публичный API не ломаем** без явного согласования.

## Как измерять

- Wall-clock полного прогона (`time ./target/release/aruna` или fixture ZIP).
- По стадиям (`read` / `parse` / `sort` / `render`) — `cli/examples/bench_parse.rs`,
  min-median-max по `ARUNA_BENCH_RUNS` прогонам, без сторонних зависимостей:
  `cargo run --release --example bench_parse -- fixtures/…zip`.
- Для WASM — latency поиска в браузере (Performance-профиль вкладки).

`/src/lib/search.worker.ts` и файлом `/src/data/inventory.bin.gz`, как их берёт
приложение.

Числа в этом файле относятся к сборке, на которой сняты, и устаревают вместе с
парсером — доля ZIP была 91 %, пока разбор не начал искать инвентарный номер в
теле документа. Правя профиль, перезамеряйте, а не пересчитывайте.

## Правило для будущих изменений

Любая новая «оптимизация» обязана иметь:
- цифры до/после,
- краткое обоснование,
- отсутствие заметного ухудшения читаемости.

Иначе — откат.
